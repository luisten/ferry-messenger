# On-device spike: Instagram DMs without the server (2026-10-16)

> Account names in this file are the fictional stand-ins (`tamoveska` personal, `kivostudio` professional).

**Status: final.** Question: can Ferry talk to Instagram straight from the phone, with no Synapse and no bridge?
**Answer: yes for chatting; push needs a small relay.** mautrix's Instagram client library ran unmodified inside an
iOS app and did login, inbox, send, live receive, resume and catch-up with a dummy account. Instagram web push
reached us only through a standard push service (Mozilla's), not at our own URL, so notifications need an always-on
relay that holds a push-service connection (see Web push).

Setup: `mautrix/meta` tag `v0.2609.0` (`dec2e1e`, the version the dev bridge runs), Go 1.27.1 (go.dev tarball,
sha256-checked, outside the repo), Xcode 27.0, iPhone 17 simulator on iOS 26.4. The spike logged in as `tamoveska`
through its own web view; the dev stack stayed up with both dummies. Nothing in Ferry's app or server changed.
Simulator only, text only, one account at a time.

## How it was built

- **Wrapper:** a `package main` with cgo exports (`cmd/igspike`, about 170 lines, kept outside the repo) over
  `pkg/instameow`:
  - `IGStart(cookies JSON)`: `NewClient` (`DisableTyping: true`), `LoadIndex` (index page + mailbox), then
    `go Connect`;
  - `IGNextEvent(timeout)`: events as JSON, polled from a Swift background task. The state dump (web tokens) and
    cookies never leave Go;
  - `IGSendText(thread IGID, text)`: `SendMessage` with `ig_thread_igid`, an `offline_threading_id` from
    `methods.GenerateEpochID()` and `send_attribution: igd_web_chat_tab:in_thread`, as in
    `msgconv/igconv/from-matrix.go`;
  - `IGRegisterWebPush(endpoint, p256dh, auth)`: `RegisterPushNotifications` (`device_type: web_vapid`);
  - `IGStats`, `IGStop`.
- **Build:** no gomobile. Go's c-archive mode with Xcode's clang, once per SDK:
  `CGO_ENABLED=1 GOOS=ios GOARCH=arm64 CC="$(xcrun --sdk iphonesimulator -f clang) -isysroot <sdk> -target
  arm64-apple-ios17.0-simulator" go build -buildmode=c-archive -trimpath -ldflags="-s -w"` (and `iphoneos` /
  `arm64-apple-ios17.0`), then `xcodebuild -create-xcframework`. 14 s. The Go linker takes the platform from the cgo
  objects (simulator slice: `LC_BUILD_VERSION` platform 7).
- **App:** one SwiftUI file built with `swiftc` (no Xcode project), the generated header as the bridging header,
  linked with `-ligcore -framework CoreFoundation -framework Security -lresolv`, ad-hoc signed, bundle ID
  `com.example.igspike`. Login: `WKWebView` on a `.nonPersistent()` store, the bridge's eight cookies and its
  `wait_for_url_pattern` (as Ferry's `CookieGate`). Cookies stayed in memory, so each rebuild needed a new login.
- **Dependencies:** `go list -deps ./pkg/instameow` for `GOOS=ios` has no cgo package. `pkg/instameow` itself doesn't
  import bridgev2, but `messagix/loginerrors` does, which drags six bridgev2 packages (database included) into the
  binary as dead code.

## Web push

Three runs, each with a fresh key pair (`p256dh` + `auth`, generated on the Mac) and `RegisterPushNotifications`
(`device_type: web_vapid`) from the spike as `tamoveska`. Every registration returned `ok` (0.64–0.85 s).

| Run (UTC) | Endpoint | `tamoveska` online elsewhere | Trigger | Result |
|---|---|---|---|---|
| 01:55 | own URL (webhook.site) | yes, dev bridge running | `kivostudio` via the dev bridge, 01:56:09 | nothing by 01:58:48 |
| 02:13 | own URL (webhook.site) | no: dev bridge stopped, spike closed | `kivostudio` from the Instagram app on a phone | nothing by 02:28:29; the phone's Instagram app (both dummies logged in) did get the push |
| 02:24 | Mozilla autopush (`updates.push.services.mozilla.com`) | no: same as above | same | **arrived 02:29:05**, under 1 s after the message's own timestamp |

- Instagram accepts any endpoint at registration but only delivered to the standard push service. One run each, so
  "custom endpoints are dropped" is the likely reading, not a proven rule (webhook.site itself could be filtered).
- The Mozilla client (`cmd/autopush`, about 100 lines, kept outside the repo): websocket to
  `wss://push.services.mozilla.com/` (subprotocol `push-notification`), `hello` with `use_webpush`, `register` with a
  new channel ID and Instagram's VAPID key (`igconnector/push.go`), then `ack` and `unregister` after the push.
- The push came as legacy `aesgcm` (Mozilla passes `crypto_key` and `encryption` with the data) and decrypted with
  `messagix/pushcrypto` to `type: direct_v2_text`, the message text (`message`, `params.im`), the sender's handle
  (`t`, `params.it`), the message ID (`params.mid`), thread IDs, the sender's picture URL (`params.a`), a badge count,
  `collapse_key: direct_v2_message` and `time_to_live: 21600`. The JSON is about 1.6 KB, mostly the picture URL.
  That is enough for a Notification Service Extension to show a full notification without connecting.
- So notifications for an on-device Ferry need a relay: an always-on process holding one push-service connection
  (autopush allows many channels per connection, so one per phone), forwarding each push's ciphertext and its two
  headers to APNs. The keys stay on the phone; the relay never sees text. Needs the paid Apple Developer account.
  Whether Mozilla's service may be used this way is a terms question to check. The other route is Instagram's
  Android push (FCM sender in `igconnector/push.go`, native login only on mautrix `main`), which also needs an
  always-on FCM connection.

## Instagram actions

Four web logins to `tamoveska` (by hand), four index + mailbox loads, six socket connections, three push
registrations, four texts (one from the spike, one from the dev bridge, two from a phone), and one "Seen" from the
dev bridge's implicit read receipt when it sent. The dev bridge was stopped 02:13–02:20 and 02:25–02:30 UTC.
Left on Instagram: four web sessions for `tamoveska` (cookies gone; removable under "Where you're logged in") and two
web push registrations pointing at deleted webhook.site URLs. The Mozilla channel was unregistered.

## What it means for Ferry

- An on-device Ferry needs no server for chatting: the Matrix glue (`pkg/igconnector`, about 4,000 lines) maps onto
  the same client calls the wrapper used (`LoadIndex`, `Connect`, `SendMessage`, `PaginateMessages`, `MarkRead`,
  …). The session would live in the Keychain.
- Decisions it needs: AGPL-3.0 code in the app, the zero-dependency rule, and notifications: none (as today), the
  Instagram app for notifications, or a push relay (small, but always on, and a paid Apple account).
- Not covered: a real device, media and voice notes, two accounts at once, history paging, the Notification Service
  Extension's memory limit.
